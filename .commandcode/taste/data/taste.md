# data
- Model known sets of external platform/social links in content schemas as named optional URL fields per platform (e.g., `apple`, `spotify`, `youtube`, `linkedin`, `x`) rather than generic `{ platform, url }[]` arrays — enables fixed deliberate display order, 1:1 icon mapping, and per-field Zod URL validation. Confidence: 0.70
- Query files in `src/app/queries/` should use content collections instead of redefining them inline. Confidence: 0.65
- Always use specific query files by domain (e.g., `playlist.ts`, `user.ts`) rather than lumping unrelated queries into a generic file like `application.ts`. Confidence: 0.85
- Apply data transformations like sorting in the query layer (server queries), not in page components. Confidence: 0.70
- When exporting/downloading R2 data, include ALL keys/objects (all applications), not filtered subsets like only "accepted" status. Confidence: 0.70
- Sort AI analysis results (how heard, story themes) by count in descending order (most frequent first). Confidence: 0.75
- Associate social links with the person they belong to: model guest and host socials (LinkedIn, X, etc.) on the person/guest entity in the content collection schema, separate from episode/platform links (YouTube, Apple, Spotify) — and when a link is mis-attached (e.g., a guest's LinkedIn shown as an episode video link), fix the content collection schema rather than repurposing it in components. Hosts should get socials modeled just like guests. Confidence: 0.70
- When the user requests UI copy that names a specific person/entity (e.g., a trailer caption "Sam Odio introduces {podcast}"), still derive those names from content data (hosts array, podcast name) rather than hardcoding them — even though a person was named in the request, keep the caption data-driven so it stays correct for whichever item is featured. Confidence: 0.65
- For event-related lookups (e.g., "next upcoming event" for application approval emails), use the content collection as the source of truth — not the Luma API. Treat the content collection as the canonical event schedule and store the external Luma URL as an attribute (e.g., `lumaEventUrl`) on each collection entry. Use a `waitlist` flag on collection entries to branch behavior: when the next event is upcoming and `waitlist: true`, the URL is included and the applicant is added directly; when there is no upcoming event, the email omits the event URL/registration code and the applicant is added to the waitlist to be notified of the next event. Confidence: 0.80
- Event CTA copy must be driven by the event's registration state, not a generic placeholder — an upcoming event with open registration should never show "Details coming soon". Drive the CTA from content flags: external `lumaEventUrl` → "Register now" linking out; `waitlist: true` (registration goes through the apply flow) → "Register" linking to /apply; reserve "Details coming soon" only for events with no registration mechanism yet. Apply the same CTA on every surface the event appears (home featured section, community events index, event detail page). Confidence: 0.75
- Content text fields that are authored with markdown (e.g., host bios containing `[text](url)` links) must be rendered as formatted markdown/real links in the UI — never displayed as literal markdown source. When a bug report flags markdown not rendering, the expectation is that authored markdown renders faithfully wherever the field is surfaced. Confidence: 0.60
- Prefer the content pipeline's native markdown feature over bespoke custom renderers: when a hand-rolled markdown-to-React/HTML helper is introduced in a UI component, the user will ask whether content collections (e.g., `compileMarkdown` in the transform, which already processes the document body) can do the rendering instead — use platform-native markdown handling at the data layer where it cleanly fits, and only fall back to a per-component lightweight helper when the pipeline doesn't support the case (e.g., inline frontmatter strings). Confidence: 0.5
